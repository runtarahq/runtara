# Adding or changing an integration agent

How to add a workflow agent for an external service, or change one, end to end.
Written for people and coding assistants alike; the rules in
[For coding assistants](#for-coding-assistants) are binding for assistants.

## Choose the path

| The service has… | Do this |
| -- | -- |
| An official OpenAPI 3 or Swagger 2.0 spec | [Generate the agent](#generated-agent) with `scripts/connector_gen` |
| No usable spec, or behaviour the spec cannot express | Write the agent by hand; `crates/agents/runtara-agent-stripe` is the reference |
| A plain HTTP API nobody needs typed capabilities for | Add only a [connection type](#connection-type); the generic `http` agent can then call the service with it |

`fetch` refuses operations the generator cannot send correctly: form-encoded or
multipart request bodies (a Swagger 2.0 operation that also `consumes` JSON is
sent JSON), object query parameters without declared scalar fields or in a
style other than `deepObject` or exploded `form`, array query parameters of
objects or in a style other than `form`, and required cookie parameters. Such an operation
needs a hand-written capability, or the generic `http` agent.

## For coding assistants

- Never edit `crates/agents/*/src/generated.rs`, `spec.slice.json` or the
  fetched `tests/fixtures/*.json` by hand. Change `connector.yaml` and run
  `connector_gen.py fetch` / `generate` instead.
- Get explicit approval from the user before changing a generated file in any
  other way, and before touching `scripts/connector_gen/templates/`. A
  template change affects every generated agent: regenerate all of them and show
  the diff.
- Do not update a `connector.yaml` sha256 pin without showing the user what
  changed in the vendor's spec.
- Do not add capabilities by hand to a generated agent: list the operation in
  `connector.yaml`. The templates cannot yet include hand-written capabilities,
  so a vendor quirk that needs one is a template change (see the rule above).
- When a vendor's spec does not fetch, generate or compile, fix
  `connector_gen.py` (or, with approval, the templates) so the spec works as
  published, add a test to `test_connector_gen.py`, and say so in the change's
  description: it is a gap in the generator, not in the agent.
- A crate under `crates/agents/` must be registered in
  `runtara-agent-bundle-emit` in the same change, or the server fails at boot.

## Generated agent

Tool setup and the `connector.yaml` format: [scripts/connector_gen/README.md](../scripts/connector_gen/README.md).

### What is generated and what is written by hand

Generated by `connector_gen.py`, committed, never edited:

| File | Produced by | Contents |
| -- | -- | -- |
| `crates/agents/runtara-agent-<id>/spec.slice.json` | `fetch` | The vendor's spec trimmed to the listed operations and the schemas they use, annotated with labels, examples, defaults and `x-runtara-*` extensions |
| `tests/fixtures/<operationId>.json` | `fetch` | The spec's own 2xx response examples |
| `src/generated.rs` | `generate` | Input structs (parameters and flattened body fields), output types and enums, one `#[capability]` function per operation, `agent_info()`, `agent_component!` |

`runtara_agent_<id>.wasm` and `.meta.json` are build artifacts of
`scripts/build-agent-components.sh`, not committed.

Written by hand for each new agent:

| What | Where |
| -- | -- |
| `connector.yaml`: agent id, name, description, `integration_id` (one connection type or a list), error prefix, spec URL and sha256 (or several specs, as UPS publishes them), operations, label overrides, body envelopes, headers and credential parameters the connection sends, pinned path parameters, input types the spec gets wrong | the crate |
| `Cargo.toml`, `src/lib.rs` (copied from `runtara-agent-pipedrive`), `src/kit.rs` (copied from `runtara-agent-shippo`) | the crate |
| Tests: response examples round-trip, metadata lists the capabilities and inputs, inputs build the expected requests | `tests/*.rs` in the crate (`runtara-agent-zendesk` shows envelopes and pagination) |
| Registration: path dependency and `agents()` entry | `crates/runtara-agent-bundle-emit/Cargo.toml`, `src/main.rs` |
| A [connection type](#connection-type), unless an existing one fits | `runtara-agents` (params, extractor, two registries, tests), `runtara-connections` (auth arm, rate-limit default, tests), form snapshot |
| Optional icon | `service-icon.tsx` |
| Release note | `CHANGELOG.md` |

Not needed per agent: UI code (connection forms and the step editor render
from metadata), CI changes (the check finds every `connector.yaml`), and the
workspace `Cargo.toml` (it includes `crates/agents/*`).

1. **Pick the operations.** Curate the capabilities users need; the full spec
   can have hundreds of operations. Field labels are derived from the spec;
   fix any that read badly with `labels:` in `connector.yaml`.
2. **Create the crate** `crates/agents/runtara-agent-<id>/`, copying
   `runtara-agent-pipedrive`:
   - `Cargo.toml` with `crate-type = ["cdylib", "rlib"]` and the same
     dependencies;
   - `connector.yaml` with the agent id, the spec URL and its sha256, and the
     operationIds;
   - `src/lib.rs` with `pub mod kit; mod generated; pub use generated::*;`;
   - `src/kit.rs`, the request builder and error envelope the generated code
     calls, copied from `runtara-agent-shippo` with Shippo's wording and id
     field replaced. A request that is not a read and gets no answer, a 5xx or
     an answer it cannot read fails as `<PREFIX>_OUTCOME_UNKNOWN` and is not
     retried: the vendor may have carried it out, and sending it again can
     create a second record. A 429 is still retried, because the vendor refused
     the request. Retry a write only if sending it twice leaves the same result
     as sending it once, and say why in the kit. Check each capability, not just
     its HTTP method: `runtara-agent-pipedrive` retries PATCH and DELETE, but
     `runtara-agent-zendesk` retries only DELETE, because updating a ticket adds
     its comment again.
3. **Fetch and generate:**
   ```bash
   PY=scripts/connector_gen/.venv/bin/python
   $PY scripts/connector_gen/connector_gen.py fetch crates/agents/runtara-agent-<id>
   $PY scripts/connector_gen/connector_gen.py generate crates/agents/runtara-agent-<id>
   ```
4. **Register the agent** in `crates/runtara-agent-bundle-emit`: a path
   dependency in `Cargo.toml` and an entry in `agents()` in `src/main.rs`.
5. **Add or reuse a [connection type](#connection-type)** whose
   `integration_id` matches `agent.integration_id` in `connector.yaml`. An
   agent that accepts several credential flows for one API (an OAuth client
   and an API token, say) lists all of them there.
6. **Add tests** like `runtara-agent-pipedrive/tests/examples.rs`: the spec's
   response examples deserialize and round-trip, the metadata lists the
   expected capabilities and inputs, and representative inputs build the
   expected method, path, query and body.
7. **Add a release note** to `CHANGELOG.md`.
8. **[Verify](#verify).**

To change an existing generated agent, edit its `connector.yaml` (operations,
spec pin) and repeat steps 3, 6 and 8.

### How the generated file is wired in

```
connector.yaml + spec.slice.json
  └─ connector_gen.py generate ─► src/generated.rs
       ├─ capabilities, input/output types, agent_info()
       └─ agent_component!  ─► wasm export runtara:agent-<id>/capabilities
src/lib.rs: mod generated; pub use generated::*;
crates/runtara-agent-bundle-emit: agents() calls runtara_agent_<id>::agent_info()
  └─► runtara_agent_<id>.meta.json
scripts/build-agent-components.sh: builds every crates/agents/* crate, emits the
  meta.json files, fails if a .wasm has no meta.json, stages both into
  target/agent-components
server boot: publishes RUNTARA_AGENT_COMPONENTS_DIR as its agent release in the
  artifact store (an agent .wasm without its .meta.json is refused) and loads
  the agents from that release
```

## Hand-written agent

Follow `crates/agents/runtara-agent-stripe`:

- capability functions with `#[capability]`, inputs and outputs with
  `#[derive(CapabilityInput)]` / `#[derive(CapabilityOutput)]` and `#[field]`;
- calls through `runtara_http` with the step's connection id, never raw
  network or credentials;
- `agent_info()` listing every capability, input and output type, and
  `agent_component!` listing every capability function.

Then do steps 4–8 of the generated path.

## Connection type

Needed when the service's authentication or base URL is not covered by an
existing connection type (`http_bearer`, `http_api_key`,
`http_oauth2_client_credentials`, `http_oauth2_authorization_code`, …).

1. `crates/runtara-agents/src/agents/extractors/connection_types.rs`: a
   `#[derive(ConnectionParams)]` struct with `#[connection(integration_id = …,
   category = …, auth_type = …)]` and its `HttpConnectionExtractor`.
   - `category` must be a `ConnectionCategory` (`ecommerce`, `file_storage`,
     `llm`, `crm`, `erp`, `database`, `email`, `messaging`, `payment`, `cloud`,
     `api`); anything else is a compile error. A new category is its own
     change: the enum and its `ALL`, `id`, `display_name`, `description` and
     `parse` in `runtara-dsl/src/agent_meta.rs`, the category match in
     `runtara-agent-macro`, `category-icons.ts` and `CATEGORY_ICONS` in
     `service-icon.tsx`, and the regenerated frontend API client.
   - `auth_type` is a `ConnectionAuthType`: `api_key`,
     `oauth2_client_credentials`, `oauth2_authorization_code`, ….
   - When the host depends on the account (a subdomain, a region), build the
     base URL in one function that validates the value, as
     `zendesk_base_url` does, and use it in the extractor (an invalid value is
     an error) and in step 4 (an invalid value leaves no base URL, so a
     credentialed request fails closed at the proxy's pin step).
2. `crates/runtara-agents/src/agents/extractors/mod.rs`: add the extractor to
   `HTTP_EXTRACTORS`. This also lets the generic `http` agent use the
   connection.
3. `crates/runtara-agents/src/static_registry.rs`: add the
   `__CONNECTION_META_<Struct>` entry.
4. `crates/runtara-connections/src/auth/provider_auth.rs`: a match arm that
   injects the credential and sets the base URL.
   - OAuth2 authorization-code types are descriptor-driven: add the
     `integration_id` to the existing `hubspot_private_app | quickbooks_online
     | …` arm instead.
   - OAuth2 client credentials against the vendor's own token endpoint get a
     `describe_<vendor>_client_credentials_auth` returning
     `DeferredAuth::OAuth2ClientCredentials` (Shopify, Zendesk): the token is
     minted, cached and injected at request time. Send the body the vendor
     documents (`TokenRequestBody::Json` or `FormUrlEncoded`), and ask for a
     token lifetime when the vendor's default is a token that never expires.
5. `crates/runtara-connections/src/util/rate_limit_defaults.rs`: a default
   rate limit from the vendor's documented limits, or, only when they are
   genuinely unknowable, an entry in `RATE_LIMIT_OPT_OUT`. Required: a test
   fails for any connection type with neither. Connection types for the same
   API share one default.
6. Tests: the extractor in `runtara-agents/src/agents/extractors/tests.rs`
   (headers, base URL, registration, a rejected host), the match arm in
   `provider_auth.rs`, and the default in `rate_limit_defaults.rs`.
7. Optional: an icon in
   runtara-frontend's `src/shared/components/service-icon.tsx`,
   keyed by the connection type's `integration_id` (it falls back to the
   category icon).
8. Refresh the connection form snapshot:
   ```bash
   UPDATE_CONNECTION_FORM_SNAPSHOTS=1 cargo test -p runtara-connections --test form_definition_snapshots
   ```

## Declared connection type

An agent built outside this repository cannot add
a connection type: connection types are compiled into runtara. When the
service authenticates the way a generic type does (HTTP Basic, an API-key
header or a bearer token against one base URL), the agent can instead
**declare** a branded preset of that type. Users then connect the vendor by
name and fill in the vendor's fields.

The declaration is a `runtara_dsl::derived_connection::DerivedConnectionType`,
written into the agent's `meta.json` under `connectionTypes` with
`runtara_dsl::derived_connection::agent_meta_document`. The agent lists the
declared type's id in its `integration_ids`.

```json
"connectionTypes": [{
  "integrationId": "example_crm",
  "displayName": "Example CRM",
  "category": "crm",
  "basedOn": "http_basic",
  "baseUrl": "https://{account}.vendor.example/api",
  "params": [{ "name": "account", "displayName": "Account",
               "pattern": "^[a-z0-9]([a-z0-9-]{0,61}[a-z0-9])?$" }],
  "fields": [{ "name": "username", "displayName": "API user" },
             { "name": "password", "displayName": "API password" }],
  "iconUrl": "https://cdn.example.com/icons/example-crm.svg"
}]
```

- `basedOn` is one of `http_basic`, `http_api_key` or `http_bearer`.
- `params` are fields of the declared type that only fill `baseUrl`'s
  placeholders. Each needs an anchored `pattern`; values must also match
  `[A-Za-z0-9_-]{1,63}`. The host of `baseUrl` must end in at least two
  literal labels, so a value chooses the vendor's tenant and never another
  host.
- `fields` relabel the base type's fields. `fixed` gives base fields a
  value the user cannot change, such as `header_name` for `http_api_key`.
  The base's `base_url` is never a user field, and secrecy is always the
  base's.
- `iconUrl` is an `https://` URL, served by the CDN rather than by runtara.

At boot the server registers the declarations of the agents in its release
(`runtara_agents::derived::register`), and an invalid one stops it. From then
on the type is listed, found, validated and rendered like a built-in one. A
connection of it authenticates as its base type, with its parameters turned
into the base's (`DerivedConnectionType::to_base_parameters`). Values that do
not render leave no base URL, so the proxy refuses the request. Rate limits
are the base type's. The type is offered only to tenants entitled to an agent
that declares it (`runtara_connections::AgentAccess`).

Use a compiled [connection type](#connection-type) instead when the service
needs an OAuth flow, request signing, or anything else a generic base cannot
express.

## Verify

```bash
cargo fmt --all -- --check
cargo clippy -p runtara-agent-<id> --all-targets -- -D warnings
cargo test -p runtara-agent-<id>
scripts/connector_gen/.venv/bin/python scripts/connector_gen/connector_gen.py check crates/agents/runtara-agent-<id>
cargo build -p runtara-agent-<id> --target wasm32-wasip2 --release
scripts/build-agent-components.sh
```

With a new connection type, also run
`cargo test -p runtara-agents -p runtara-connections` and
`cargo clippy -p runtara-agents -p runtara-connections --all-targets -- -D warnings`.
A change to `connector_gen.py` or the templates also needs
`scripts/connector_gen/test_connector_gen.py` and `check` over every
generated agent (`$(dirname crates/agents/*/connector.yaml)`), as CI runs them.
