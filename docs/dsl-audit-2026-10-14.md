# Workflow DSL audit

Audit date: 2026-10-14, at `520f304f2`. Scope: the workflow DSL as a whole.
That covers the types in `crates/runtara-dsl/src/schema_types.rs`
(`DSL_VERSION` 3.5.0), the validator in `crates/runtara-workflows/src/validation*.rs`,
the direct emitter in `crates/runtara-workflows/src/direct_wasm`, the guest runtime
in `crates/runtara-workflow-stdlib/src/direct_json.rs`, and the other places that
describe the DSL: the MCP authoring schema, `/specs/dsl`, the frontend and the docs.

## How each finding was reproduced

Every finding was pushed through a real workflow on an isolated `runtara-server`
built from this commit (its own port, database, Valkey and tenant; your dev
server on :7001 was never touched). A6 and A11 instead ran in the direct-wasm
execute harness: a real compile and real components in wasmtime, with a
scripted provider. What a run can show depends on the kind of finding, so each
row in the [ledger](#reproduction-ledger) states which of these it is:

- **Ran:** the workflow saved, compiled and executed, and its output or error
  shows the problem. This covers every A finding, B1, B5, B8, C3–C10, and the
  behavioural D items.
- **Refused:** the workflow can't be authored at all. For these findings the
  refusal is the behaviour: a misleading error, an accepted-looking spelling
  rejected, a field the doc promises being unknown. This covers B2, B6 (E110),
  B7, B9, C1, C2, most D casing, placement and vocabulary items, and the
  rejected doc examples and example files (E1, E6, E7, E9).
- **Compile-only failure:** the workflow saves cleanly and then fails to
  compile. This covers B3, B4, B6 ("" label) and the non-durable Delay.
  Executing such a workflow anyway returns "queued" for a run that never
  exists (B11).
- **Following the docs:** for findings that are wrong documentation, a
  workflow does what the docs say and the behaviour contradicts them. Examples:
  - E8: call the MCP tool the prose names → `"tool not found"`.
  - E7: fetch the crate version the README says to add → crates.io 404 "does not have a version `4.0.0`".
  - E7: open the schema file the README cites → 404; ask for workflow-backed reports → 404.
  - E4: run GroupBy, which the changelog says was removed → it runs (C9).
  - E10: run a `template` mapping the doc omits → `"42"`; set Agent `timeout:0`, which the editor calls warning-only → the run fails.
  - E9: SetState/GetState, which a frontend comment calls "not compiled" → state round-trips.

The editor findings (E9 pickers) were observed in the real editor, built from
this worktree, on workflows created for the check, and those workflows were
then executed. The runtime handles the `file` hint that the editor can't show.

Two earlier verification passes are kept as supporting evidence only: an
**audit-probe workflow** (run `41a73b2e-…`, 75/75) that re-issued the
validator, save and compile calls and checked the doc and source text from
inside a run, and a scratch binary that called `build_source` and the shared
`condition_eval` directly. The text checks prove the wording exists; the
behaviour is shown by the runs above. The probe's first run (`8c09cb4b-…`) is
also live evidence for C4: its Agent `inputMapping` rewrote reference envelopes
inside the graphs it was sending.

Where a repro contradicted the original claim, the finding was corrected or dropped
(see [Corrections](#corrections-from-reproduction)).

Findings are ranked:

- **A. Silently wrong at runtime.** The workflow runs and gives the wrong result.
- **B. Validation and runtime disagree.** One accepts what the other rejects, or
  saving succeeds and compiling fails.
- **C. Ambiguity.** Two legal spellings, or a name that means two things.
- **D. Gaps and inconsistencies in the language design.**
- **E. Doc, example and surface drift.**

## D. Gaps and inconsistencies in the language design

Every item below was reproduced.

- **Typos are dropped silently outside step structs.** Step structs reject unknown fields; graph, edge, schema-field and variable structs swallow them. **[run]** `inputSchema.name.requird: true` validated clean, and executing with `{}` *completed* with `n: null`; with `required: true` it was rejected. Some typos are caught only as a side effect: `exectionPlan` gave E003/E012, `lable` gave E003, `conditon` gave a misleading E073 fan-out error.
- **`Variable.type` is never checked.** **[save]** `{"type":"integer","value":"hello"}` validated, saved and compiled.
- **`config` is optional where its contents are required.** **[save][run]** a Split with no `config` validated and compiled, then failed at runtime with "config missing value".
- **Some dynamic fields are checked only at runtime.** **[save][run]** `Delay.durationMs: "5s"` was valid at save and failed at runtime with "duration_ms must be a number".
- **`visibleWhen` with both `equals` and `notEquals`, or with neither, is accepted.** **[save]**
- **Collection steps disagree on null input.** **[run]** Filter over null gave `{items:[], count:0}`. Split over null failed, and still failed with `convertSingleValue:true`.
- **`timeout: 0` means opposite things.** **[run]** Agent `timeout:0` failed with `AGENT_TIMEOUT`; Split `config.timeout:0` ran normally.
- **AiAgent has no step-level `timeout`.** **[save]** "unknown field `timeout`".
- **onError inside an onError handler is ignored without a warning.** **[save][run]** the graph validated clean; the inner failure failed the run instead of reaching its handler.
- **Log and Error messages are verbatim,** although `template` exists as a mapping type. **[run]** Log stored `message: "x={{ data.x }}"`, and the Error message was literal.
- **Three type vocabularies that don't line up.** **[save]**
  - The reference hint `array` is rejected (the hint vocabulary is string/integer/number/boolean/json/file).
  - The variable type `json` is rejected, and so is the variable type `connection`.
  - The schema field type `json` is rejected.
- **Enum casing is inconsistent.** **[save]** `CompactionStrategy` accepts only `slidingWindow` (both `sliding_window` and `SLIDING_WINDOW` are rejected). Switch `matchType` is SCREAMING_SNAKE (`eq` is rejected). **[save]** `stepType` is PascalCase (`agent` is rejected), `valueType` is lowercase (`Reference` is rejected), and the API's `memoryTier` is uppercase (`xl` gives 422 "expected one of S, M, L, XL"). **[run]** the GroupBy output key `total_groups` is snake_case (C9).
- **`SwitchMatchType` doesn't cover what its doc says.** **[save]** `AND` and `LENGTH` are rejected, contrary to "supports all ConditionOperator values".
- **Timeout and retry fields are named and placed inconsistently.** **[save]** Agent `timeoutMs`, WaitForSignal `timeout`, Agent `config.maxRetries`, Split step-level `maxRetries` and While `config.maxRetries` are each rejected as unknown fields. **[run]** WaitForSignal `timeoutMs:2000` *failed* the run (`WAIT_TIMEOUT`), while WaitForInstances `timeoutMs:2000` on an 8 s child *completed* with `resolution:"deadline"`. `executionTimeoutSeconds:2` stopped an 8 s run at about 3 s ("Execution timed out"), so it is in seconds, unlike every other timeout field. Details:
  - Timeout fields: Agent `timeout` is in ms, Workflow `executionTimeoutSeconds` is in seconds, WaitForInstances `timeoutMs` settles rather than fails, and AiAgent has `turnTimeout`.
  - Retry fields: on the step for Agent and Embed, under `config` for Split and AiAgent.
  - While, WaitForSignal, WaitForInstances, SetState and GetState accept onError but cannot retry: **[save]** `maxRetries` on each is rejected as an unknown field.
- **`Workflow.memoryTier` and `Workflow.trackEvents` in the DSL are never read** (the database columns are authoritative). **[run]** `trackEvents:false, memoryTier:"S"` inside the graph were silently dropped: 5 step events were still recorded, and the workflow stayed `trackEvents:true, memoryTier:"XL"`. C8 shows the same for top-level `durable`.
- **Delay with `durable:false`, and any Delay in a non-durable workflow, passes validation and then fails to compile.** *Found during reproduction.* **[save]** both shapes were valid and saved, then failed with "direct workflow compiler does not support this graph yet: d:non-durable-delay". The field doc (`schema_types.rs:1084-1086`) describes a working non-durable sleep. Either implement it, or reject it in validation and fix the doc.

## Suggested order of work

1. **A0 first.** It affects every workflow that declares a variable and runs through the server.
2. **The other runtime bugs: A1–A4, A13 and B11** (B11 silently drops runs). Each is local, with a clear regression test.
3. **Inheritance into nested graphs (A5–A7):** budget, variables and durability need one rule, applied everywhere.
4. **Move compile-only errors into validation (B3, B4, B6, B9)** and fix the misleading messages (B2, B7, B8).
5. **One condition evaluator (B1).**
6. **Decide or deprecate:** `sequential`, `pollIntervalMs`, `default`/`nullable`, loop `maxRetries`, and the workflow-level `durable`/`memoryTier`/`trackEvents` (A8–A11, C8).
7. **Tighten parsing (D):** `deny_unknown_fields` on `ExecutionGraph`, `ExecutionPlanEdge`, `SchemaField` and `Variable`; enforce `Variable.type`; make `config` required where its contents are; add a tagged `ChildVersion`. Check this against stored workflows first.
8. **Docs and surfaces (E)**, with a test that parses every JSON example in doc comments and in `examples/`.
9. **Language-level consistency** (timeout/retry naming, enum casing): breaking changes, so batch them behind DSL 4.0.

Prior audits already cover the step-editor reference picker and the 14 direct-emitter DSL gaps (all resolved). None of their items are repeated here.
